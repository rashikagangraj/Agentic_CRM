01

Sandbox runner — free-text input support

Resolved

aiKart's "Try Me" sandbox invokes the Docker image directly (aikart-run mode) with a JSON payload on AIKART_INPUT — not through the web app. Its UI has two shapes: a structured Batch Mode form matching the manifest's inputs, and a single free-text chat box with no fields at all (not even workflow). The runner only handled the first shape.

Fix — new endpoint Added POST /api/marketing/extract (Gemini-backed, server-side) that pulls businessName, niche, category, and the rest of the structured fields — plus workflow itself — out of a plain-language request. runner.mjs calls it only when required fields are already missing, so the documented structured path pays zero extra cost.
Bug — wrong resolution path First attempt imported @google/genai directly into runner.mjs. Failed at runtime: Next.js's standalone build compiles that SDK into its own server chunks rather than leaving it as a resolvable package, so an external script can never import it. Fixed by routing through HTTP to the app's own route instead — the same pattern the runner already used everywhere else.
Bug — merge order silently dropped a field normalizeInput() unconditionally set input.contentFormat = input.contentFormat || raw.format, creating an explicit undefined property even when neither source had one. The later merge, { ...extracted, ...input }, then let that undefined silently overwrite a correctly-extracted value. Rewrote the merge as an explicit loop that only replaces empty/missing keys.

Also found genuine LLM non-determinism: category and niche overlap in casual phrasing, so extraction omits category roughly 1-in-3 calls. Since it's only ever used as prompt context (never branched on), it now defaults to "services" instead of hard-failing a run that has everything else it needs. Verified across 3 repeated identical calls.

02

YAML manifest — stale image tag

Resolved

aikart-manifest.yaml's runtime.image had regressed to 1.0.6 — four versions behind — while listing-manifest.yaml and Dockerrun.aws.json stayed correctly at the current build. Almost certainly the real cause behind reports of the agent "not taking input": if that file was what got uploaded, the live sandbox would run pre-extraction code that requires every structured field with no fallback at all.

  • Re-synced all three deployment references to the same tag on every version bump from here on (1.0.7 → 1.0.9)
  • inputs schema itself was already correct the whole time — all 12 fields, workflow and tone as selects, required/optional flags — no changes needed there
  • No customer data (business names, cities) ever hardcoded into the manifest — checked directly, confirmed clean
03

Gemini API — retired model

Resolved

Tested the real GEMINI_API_KEY directly against Google's endpoint. Key was valid — but both API routes were hardcoded to gemini-2.5-flash, which Google has retired. With a live key, every AI call would have failed outright.

Fix Swapped to gemini-3.6-flash in research/route.ts and generate/route.ts. Confirmed working — first genuine end-to-end AI output all project, both through the local dev server and inside the Docker image.
04

AWS Elastic Beanstalk

Diagnosed & prepped

Environment health showed Expected version "Sample" (deployment 1). Pulled eb-engine.log directly — the running container was a Python process on port 8000, EB's own placeholder app, not ours at all.

  • Root cause: Dockerrun.aws.json was likely zipped with the file nested in a subfolder rather than at the archive root — EB silently falls back to Sample when it can't find a valid Dockerrun at the top level
  • Restored HostPort: 80 in Dockerrun.aws.json and rebuilt eb-deploy.zip with the manifest correctly at the zip root
  • Confirmed the empty NEXT_PUBLIC_FIREBASE_* environment properties are a red herring — those need Docker build-time baking, not EB runtime vars, and the app has a graceful demo-mode fallback regardless

Ready to upload; a confirmed successful deploy is still pending on your side.

Open — a fake-data pattern keeps reappearing

Open

The same anti-pattern surfaced three separate times today, in three different files, each time reintroduced outside this debugging session: runner.mjs silently defaulting businessName to "Target Business"; research/route.ts defaulting to "Your Business" / "Professional Services"; and, most recently, validate() silently filling in topic / tone / contentFormat for the generate workflow instead of requiring them.
